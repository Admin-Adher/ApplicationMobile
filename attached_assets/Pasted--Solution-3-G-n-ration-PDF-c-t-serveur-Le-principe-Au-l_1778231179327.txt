## Solution 3 — Génération PDF côté serveur

### Le principe

Au lieu de faire `HTML → PDF` sur le device mobile (avec ses contraintes mémoire), tu délègues ce travail à ton serveur Express :

```
App mobile                    Serveur Express (port 3001)
─────────────────             ──────────────────────────
Construit le HTML         →   Reçoit le HTML
                              Lance Puppeteer (Chrome headless)
                              Génère le PDF en mémoire serveur
Reçoit le PDF en base64   ←   Renvoie le fichier
Ouvre le share sheet
```

Le serveur a autant de RAM que tu lui donnes — 1 Go, 4 Go, peu importe. Le renderer PDF mobile n'existe plus dans l'équation.

---

### Ce que ça change côté app

```ts
// Avant — tout se passe sur le device
const { uri } = await Print.printToFileAsync({ html });

// Après — le device envoie, le serveur génère
const response = await fetch('https://ton-api.com/generate-pdf', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ html }),
});
const { pdfBase64 } = await response.json();

// Écriture locale pour le share sheet
const fileUri = FileSystem.cacheDirectory + 'rapport.pdf';
await FileSystem.writeAsStringAsync(fileUri, pdfBase64, {
  encoding: FileSystem.EncodingType.Base64,
});
await Sharing.shareAsync(fileUri);
```

---

### Ce que ça change côté serveur Express

```ts
import puppeteer from 'puppeteer';

app.post('/generate-pdf', async (req, res) => {
  const { html } = req.body;

  const browser = await puppeteer.launch({ args: ['--no-sandbox'] });
  const page = await browser.newPage();
  await page.setContent(html, { waitUntil: 'networkidle0' });

  const pdfBuffer = await page.pdf({
    format: 'A4',
    printBackground: true,
    margin: { top: '20mm', bottom: '20mm', left: '15mm', right: '15mm' },
  });

  await browser.close();

  res.json({ pdfBase64: pdfBuffer.toString('base64') });
});
```

C'est ~30 lignes. Puppeteer est un Chrome headless — il rend le HTML exactement comme un vrai navigateur, avec un support CSS parfait et aucune limite mémoire arbitraire.

---

### Les vrais avantages par rapport à la solution 1

| | Solution 1 (compression) | Solution 3 (serveur) |
|---|---|---|
| Limite photos | ~150 | **Illimitée** |
| Qualité photos | Compressée 0.55 | **Full-res possible** |
| Rendu CSS | Dépend du WebView Android | **Chrome headless = parfait** |
| Envoi email direct | Non | **Oui** — le serveur peut envoyer lui-même |
| Complexité | Faible | Moyenne |
| Coût infra | Zéro | RAM serveur + Puppeteer (~150 MB idle) |

Le point "envoi email direct" est intéressant pour toi : au lieu que l'utilisateur partage manuellement, le serveur pourrait générer le PDF et l'envoyer directement aux destinataires du rapport — sans passer par le share sheet mobile.

---

### Pourquoi ne pas le faire maintenant

Puppeteer pèse ~300 MB une fois installé et nécessite Chrome sur le serveur. Si ton Express tourne sur un petit VPS ou un container limité, c'est un vrai coût. La solution 1 couvre 99% des cas réels pour zéro coût infra — la solution 3 n'a de sens que si tu atteins régulièrement les 150+ réserves ou si tu veux le feature "envoi email automatique".
